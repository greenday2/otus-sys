L1 Norm Benchmark (Rust)

Небольшая программа на Rust для вычисления L1-нормы квадратной матрицы двумя способами:

  • rows — обход по строкам (cache-friendly, суммы накапливаются по столбцам);
  • columns — обход по столбцам (cache-unfriendly, типичный пример плохой локальности данных).

Требования

  • Rust (stable)
  • cargo (устанавливается вместе с Rust)
  • perf (Linux) — для сбора метрик производительности

Сборка проекта

Отладочная сборка: bash cargo build

Оптимизированная сборка (рекомендуется для замеров и метрик): bash cargo build --release

Запуск

Программа принимает один обязательный аргумент — способ обхода: rows или columns.

Через cargo: bash cargo run --release -- rows cargo run --release -- columns

Либо напрямую из собранного бинарника: bash ./target/release/homework1 rows ./target/release/homework1 columns

Пример вывода: 34368122880 Elapsed: 6.630694ms

Если аргумент отсутствует или некорректен — программа завершится с кодом ошибки и подсказкой: Argument "rows" or "columns" is needed! Argument must be "rows" or "columns"!

Сбор метрик через perf

Для корректных метрик используйте release-сборку и запускайте sudo perf на бинарнике напрямую (а не через cargo run).

bash sudo perf stat -r 10 -e cycles,instructions,L1-dcache-loads,L1-dcache-load-misses \ ./target/release/homework1 rows

bash sudo perf stat -r 10 -e cycles,instructions,L1-dcache-loads,L1-dcache-load-misses \ ./target/release/homework1 columns

Пример вывода:

Для варианта columns ожидаемо больше промахов L1-dcache и ниже IPC, поскольку обход по столбцам плохо использует кэш.

Примечания

  • Матрица имеет фиксированный размер 4096 × 4096 элементов типа u64 (см. matrix_size в main.rs). При необходимости измените значение в исходном коде.
  • Названия событий L1-dcache-* поддерживаются на архитектуре x86. На других платформах список доступных событий можно посмотреть командой: bash perf list

Пояснение результатов

Согласно официальным руководствам AMD по оптимизации размер кэш-линии L1 Data Cache на современных процессорах AMD64 составляет 64 байта. У процессоров Intel — тот же размер. Это значит, что любое обращение к памяти читает не «8 байт», а «64 байта».

Параметры матрицы: В коде задана квадратная матрица размером 4096 × 4096 элементов типа u64, размер каждого элемента составляет 8 байт. Если бы каждая байтовая позиция памяти читалась ровно один раз (идеальный случай), потребовалось бы прочитать:

4096 × 4096 × 8 байт / 64 байта = 2 097 152 кэш-линий

Фактические данные из профилировщика

| Метрика | rows | columns | |---------|------|---------| | L1-dcache-loads | 123 287 525 | 143 172 667 | | L1-dcache-load-misses | 8 948 999 | 29 775 124 | | Доля промахов | 7,26 % | 20,80 % | | IPC | 0,82 | 0,37 | | Время (среднее) | ~0,0885 с | ~0,2294 с |

Число промахов L1 приблизительно равно числу уникальных кэш-линий, подтянутых из памяти (L2/L3/RAM), потому что каждая промахнувшаяся загрузка инициирует выборку целой 64-байтовой линии.

  • rows: ~8,95 млн кэш-линий загружено из памяти;
  • columns: ~29,78 млн кэш-линий загружено из памяти.

Объём «бесполезно» прочитанной памяти

При обходе по столбцам в каждой подтянутой кэш-линии реально используется только 8 байт из 64 (один элемент u64). Остальные 56 байт (87,5 %) загружаются впустую и затем вытесняются, так как соседние элементы по строке не нужны до следующей итерации внешнего цикла — а к тому моменту линия уже выброшена из L1.

Объём бесполезного трафика:

(29 775 124 − 2 097 152) × 64 байта ≈ 1,77 ГБ

То есть почти 1,8 ГБ оперативной памяти прокачивается зря только из-за неудачного порядка обхода. У варианта rows этот показатель тоже ненулевой, но гораздо меньший, поскольку каждая загруженная линия используется полностью — все 8 элементов u64 подряд.

Вывод

Последовательный обход (вариант rows) оптимален (для amd64!), потому что одновременно выполняются три условия:

  1. Аппаратный префетчер распознаёт шаблон обращения к адресам и заранее подтягивает данные в L1 → низкая доля промахов (7,26 %).
  2. Каждая кэш-линия используется полностью (все 64 байта / 8 элементов u64)
  3. Цикл возможно векторизуется (но не в debug) в SIMD-инструкции AVX2/AVX-512 → высокая пропускная способность, IPC = 0,82 против 0,37.

Вариант columns все три пункта нарушены: префетчер не срабатывает, 87,5 % каждой кэш-линии уходит в мусор (≈1,77 ГБ лишнего трафика), векторизация невозможна. Результат — в 2,6 раза больше времени выполнения (0,229 с против 0,089 с) и почти в 3 раза больше промахов L1.
